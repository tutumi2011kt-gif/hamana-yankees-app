# 🏀 B案：名前選択だけを維持した週末公開の運用・承認条件

策定日：2026-11-18 JST。対象：有玉女子ミニバス、2026-11-21〜22公開を目標とする当番表アプリ。
**これは管理者承認書のたたき台であり、公開の承認・本番ルール変更・本番書込み解放を意味しない。**
開発ブランチのみ。2026年12月確定表、2027年1月下書き、本番Firebase／Hosting／GitHub mainには触れない。

## 1. 選択した操作方式（B案）

- 保護者は共通URLを開き、子どもの名前を選ぶだけ。Googleログイン／個別PIN／招待登録を要求しない。
- ×（自分の当番ができない）・○（別の人の当番を代われる）を日付タップで登録／取消。元担当者名は固定。
- 回答は保存直後に全員へ共有。ただし、**○を登録しても交代確定ではない**。交代確定は管理者が候補者本人へLINE等で直接確認した後の別操作。
- 端末のFirebase匿名UIDは「同一アプリ端末の識別子」であって保護者・子どもの本人認証ではない。別の人が名前を選んで**最初の回答を作れてしまう**。「同一UIDだけ編集可」は後からの他端末上書きを防ぐだけで、なりすまし防止策ではない。
- 保護者の名前・当番・×○は共通URLを知り匿名Firebase認証したチーム外の人にも閲覧されうる。URLを外部SNSや公開掲示板に掲載しない。流出時は共有範囲や公開方法を再検討する。

## 2. 保護者へ先に説明して承認を得る内容

- これは簡便さを優先した「名前選択方式」で、本人確認をしていない。誤入力だけでなく、別人名義の入力が起こりうる。
- 入力は即時共有されるが、管理者が本人確認するまで**交代確定として扱わない**。
- 毎回、名前・月・入力記号と日付を確認して送信する。全保護者が公開カレンダーに表示される自分の×○を確認し、身に覚えのないものは管理者に直接知らせる。
- 機種変更・別端末で自分の回答を取消できないときは、管理者による訂正を依頼する。管理者が本人に確認して訂正・削除する。
- 子どもの名前と当番日／回答が誰に見えるか、URLの配布範囲、問い合わせ先・確認頻度を事前案内する。名簿の学年・私的制限などは保護者サイトへ出さない。

## 3. 運用の安全策（チームが担当者を決める）

1. **管理者の日次確認**：回答受付期間中、目安として朝・夜の2回、全員の入力状況と不自然な×○をチェックする。公開直後数日はより頻繁に確認。確認担当・代理担当を1人ずつ決める。実施できない日は書込み受付を一時停止する運用を用意。
2. **本人への直接確認**：交代を確定する前に、「元担当者の×」と「交代候補者の○」双方をLINE・電話等、既存の連絡先で確認する。確認時刻・確認者を管理者記録へ残し、未確認のまま交代確定しない。○は全曜日選択可能、ただし現場の引継ぎ可否は直接確認。
3. **訂正経路**：身に覚えのない入力・機種変更・誤選択は管理者へ連絡。管理者専用の回答訂正画面で本人に確認後、訂正・削除。交代確定済みの日は交代解除→回答訂正→本人再確認→再確定の順。
4. **履歴／監査**：入力時の `updatedAt` と `updatedBy` (匿名UID) はあるが、削除後の履歴を保証しない。開発候補の `answerAudit` 用Cloud Functionsは、本番未配信のため、**現在の履歴監査を「稼働中」と表現しない**。公開前に、変更・削除まで追跡できる監査手段を検証するか、記録不足を含むリスクをチーム責任者が明示了承する。管理者の訂正監査も実クラウドで検証する。
5. **事故時**：保護者から報告→その日の交代確定を停止→管理者が該当回答を検証・直接確認→訂正と履歴記録→必要なら保護者全体へ周知。広範囲な不審入力を確認したら本番の保護者書込みを停止できるよう、**本番公開前に安全な読取り専用ルールへの戻し方を確認**。管理者の判断なしに本番操作を自動実行しない。
6. **入力期限**：管理者が2027年1月分の実際の締切を明示し保護者へ案内。標準は2026-12-01 00:00 JSTだが、QA画面には同日09:00 JSTが表示されていた。過去運用の「毎月5日」とも差があるため、**締切を決め直し承認が必要**。

## 4. 誰が何を承認するか（GO条件）

| 承認者 | 明示的に確認する事項 |
| --- | --- |
| チーム会長・責任者 | 名前選択によるなりすましを防止できないこと、共通URLによる氏名・当番情報の閲覧範囲、日次監視・本人確認・事故対応の運用、保護者への案内 |
| 当番表管理者（ユーザー） | 2026年12月確定表を維持、2027年1月全日程・担当・試合日、正式入力締切、監視と回答訂正の担当、交代は候補者本人に確認してから確定 |
| Firebase／GitHub管理者 | 本番Rulesの最小権限、匿名入力の作成・更新・取消の拒否試験、バックアップ、Hosting／Rules差分、監査方式、一時停止とロールバック手順 |
| 保護者各家庭 | 操作説明、名前・回答の共有範囲、なりすまし・誤入力の可能性、入力の自己確認と訂正連絡先を周知し、参加について確認する |

**ユーザーがB案を選択しただけでは、会長や全保護者の承認は完了していない。**

## 5. 技術上の最低限の確認（公開前）

- 書込み対象は2027年1〜11月の管理者が公開し受付中の「練習日」の回答のみ。2026年12月、試合・休み、未公開月、締切後は禁止。Firestore `request.time` を基準にする。
- ×は元担当者本人名義のみ、○は他の子の当番日のみ。○への既定曜日制限を強制しない。
- 回答ドキュメントのフィールドを制限。匿名UIDが更新・取消するときは**初回作成時のUIDと一致する**こと。元担当者の `ownerId` を保護者が変えられないこと。
- 確定交代後は×○回答を編集できず、管理者の交代解除が先。候補0人なら「要調整」と表示し、他人を勝手に割り当てない。
- 管理者ログイン／権限、2端末同期、異なる匿名UIDからの上書き拒否、本人名義ではない初回入力が防止できないことを**QA実クラウドで証跡付き確認**。Emulator成功と区別する。
- 管理者画面の訂正、交代確定解除、実施回数・試合中止・繰越・復元、3月下書き非公開を実クラウドで検証。匿名書込みを許可するFirestore Rulesの本番配信、保護者UIのスイッチ変更は管理者が差分を見て承認するまで行わない。

## 6. 週末公開のGO／NO-GO

- **閲覧のみ**：当番表の正確性・公開範囲・QA読取り・本番Rules・iPhone表示・本番復旧を確認し、会長と管理者が了承した場合だけGO。
- **×○入力も公開**：上記に加え、なりすましを含むリスクの明示了承、保護者への周知、直接確認・訂正・監査・事故時停止の運用、QAクラウドの書込み検証と本番Rulesの安全性・復旧試験が完了して初めてGO。
- 未完了項目を「CI成功」や「公開済みQA画面が表示できた」という理由でGOにしない。

この文書は**実装済みの安全策と運用予定を区別する**ための決定記録であり、未完了の認証・監査・QA試験を完了扱いにしない。
